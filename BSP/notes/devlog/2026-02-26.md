## [Fix] flash_stm32.sh CRLF 줄바꿈 문제

RPi에서 `./flash_stm32.sh` 실행 시 `/bin/bash^M: bad interpreter` 오류 발생.

Ubuntu에서 작성했음에도 VS Code의 `files.eol` 설정으로 인해 CRLF로 저장된 것이 원인. `.gitattributes`가 없어 git이 변환하지 않음.

RPi에서 `dos2unix`로 즉시 수정:
```bash
dos2unix flash_stm32.sh
```

재발 방지를 위해 `.gitattributes`로 `.sh` 파일을 LF 고정하는 것을 검토 중.

## [Fix] ST-Link USB 접근 권한 오류 트러블슈팅

플래시 스크립트 실행 시 장치를 찾을 수 없다는 오류:
```
ERROR usb.c: Could not open USB device 0x0483:0x374b, access error.
Found 0 stlink programmers
```

장치 자체는 인식(`0x0483:0x374b` = ST-Link VID:PID)됐으나 Linux USB 접근 권한 부족이 원인. 포트 위치와는 무관.

- **즉시 해결:** `sudo ./flash_stm32.sh ...`
- **영구 해결:** udev 규칙 추가 + `plugdev` 그룹에 사용자 등록

## [Fix] 오도메트리 누적값 → 차분값 전송으로 수정

ROS2 담당 팀원으로부터 SLAM 위치가 수십 미터씩 튀는 현상을 수정 요청받음.

원인은 `Protocol_SendOdom()`에 `Encoder_GetCount()`의 반환값(부팅 이후 누적 틱)을 그대로 넘긴 것. ROS2 노드는 50ms 주기의 차분값을 기대하고 있었음.

팀원 요청서에는 `Encoder_ResetCount()`로 하드웨어 CNT 레지스터를 리셋하는 방법을 제안했으나, `Encoder_GetSpeed()`도 동일한 CNT 레지스터를 읽기 때문에 리셋 직후 PID 루프에서 수백 틱의 오차가 발생하는 문제가 있었음. 요청서의 "각각 독립적으로 동작합니다" 주석은 오류.

하드웨어 CNT는 건드리지 않고, `main.c`의 50ms 전송 블록에 `prev_odom_L/R` static 변수를 추가해 이전 카운트와의 차이만 전송하는 방식으로 수정했다. `Encoder_GetSpeed()`의 동작에 영향 없음.

```c
// 수정 전: 누적값 전송
Protocol_SendOdom(Encoder_GetCount(ENCODER_LEFT),
                  Encoder_GetCount(ENCODER_RIGHT));

// 수정 후: 차분값 전송
int16_t cur_L = Encoder_GetCount(ENCODER_LEFT);
int16_t cur_R = Encoder_GetCount(ENCODER_RIGHT);
Protocol_SendOdom(cur_L - prev_odom_L, cur_R - prev_odom_R);
prev_odom_L = cur_L;
prev_odom_R = cur_R;
```

int16_t 뺄셈은 16비트 롤오버도 자연스럽게 처리하므로 별도 오버플로우 처리 불필요. 최대 속도(600 mm/s) 기준 50ms 내 최대 변화량은 약 282틱으로 int16_t 범위 내에서 안전.
