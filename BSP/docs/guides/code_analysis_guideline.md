# 자율주행 코드 분석 가이드라인 (Code Review Guideline)

사용자님께서 작성된 코드를 직접 분석하고 개선안을 도출하실 때 방향성을 잃지 않도록, 실무적인 관점에서의 코드 리뷰 포인트들을 정리한 가이드라인입니다. 파일별로 아래 체크리스트를 따라 코드를 한 줄씩 뜯어보시길 권장합니다.

---

## 📌 1. `drv_encoder.c` 분석 포인트 (물리량 연동 및 오버플로우)

엔코더 코드는 실제 모터가 도는 하드웨어 펄스를 `mm/s`라는 물리적 단위로 환산하는 가장 중요한 모듈입니다.

### [ ] 체크 포인트 1: 16비트 오버플로우 방어 로직 확인
- STM32F4의 타이머는 65535에서 0으로 넘어가거나 0에서 65535로 떨어지는 현상(Underflow/Overflow)이 잦습니다.
- `delta = current - prev` 부분에서 `int16_t` 자료형을 활용한 2의 보수 계산이 타이머 오버플로우를 수학적으로 어떻게 무력화시켰는지 분석해 보세요.

### [ ] 체크 포인트 2: 물리 상수 및 단위 변환
- `ENCODER_PPR`과 `WHEEL_CIRCUMFERENCE_MM` 상수가 내가 사용할 하드웨어 스펙과 정확히 맞는지 계산식을 검증해 보세요.

### ⚠️ [개선 필요 포인트]: 상태값 초기화 버그 (Critical)
- `Encoder_ResetCount()` 함수를 유심히 분석해 보세요. 이 함수는 타이머 레지스터(`CNT`)를 0으로 만들지만, `Encoder_GetSpeed()` 내부의 `static int16_t prev_left` 변수는 0으로 초기화해주지 않습니다.
- **분석 과제:** 작동 중에 `Encoder_ResetCount()`를 호출하면 다음번 속도 계산 시 어떤 폭주 현상(1-Frame Speed Spike)이 일어날지 수식으로 증명해 보고, 이 변수들을 전역(Global)으로 빼거나 초기화 함수를 수정하는 방안을 고안해 보세요.

## 📌 2. `algo_pid.c` 분석 포인트 (제어 수학 알고리즘)

PID는 현재 상태와 목표 상태의 오차(Error)를 줄이는 순수 수학 알고리즘입니다.

### [ ] 체크 포인트 1: 제어 주기(`dt`) 동기화 구조
- `PID_Init` 등에 들어가는 `dt` 값이, 메인 루프에서 이 함수를 호출하는 주파수(예: 100Hz = 0.01s)와 정확하게 일치하게 흘러가고 있는지 분석하세요.

### ⚠️ [개선 필요 포인트]: 적분 누적(Integral Windup) 방어 부재
- `pid->integral += error * dt;` 코드를 확인해 보세요.
- **분석 과제:** 로봇이 벽에 막혀 바퀴가 돌지 않는데 목표 속도가 계속 들어오면, `integral` 변수가 무한대로 커지게 됩니다. 이후 벽에서 빠져나왔을 때 로봇이 미친 듯이 튀어나가는 현상을 막기 위해(Anti-Windup), 적분값을 특정 범위 안에 가두는(Clamp) 로직을 어떻게 추가할지 고민해 보세요.

## 📌 3. `drv_motor.c` 분석 포인트 (하드웨어 모터 구동 한계)

PID의 계산 결과값(수학)을 실제 모터칩(L298N)의 PWM 듀티비(전기)로 하달하는 드라이버입니다.

### [ ] 체크 포인트 1: PWM 해상도와 타이머 주파수
- `MOTOR_PWM_PERIOD`와 `pwm_duty` 변환 공식을 보고, 속도 `600 mm/s`가 타이머의 `ARR` 값에 어떻게 매핑되는지 데이터 흐름을 추적하세요.

### ⚠️ [개선 필요 포인트]: 데드밴드(Deadband) 미처리 현상
- L298N과 같은 저가형 DC 모터 드라이버는 PWM이 너무 낮으면(예: 10% 미만) 마찰력을 이기지 못하고 고주파 소음만 내며 모터가 타버릴 수 있습니다.
- **분석 과제:** `Set_PWM()` 함수 내부에서 아주 작은 PWM 출력 명령이 들어왔을 때, 이를 0으로 완전히 꺼버리거나 최소 기동 전압(예: 15% 이상)으로 강제로 올리는 데드밴드 프리셋 로직을 어떻게 추가할지 설계해 보세요.

## 📌 4. `app_packet_parser.c` (통신 및 명령 처리 뇌)

### [ ] 체크 포인트 1: State Machine 기반 파싱
- 패킷 헤더 구조(`PROTO_HEADER1`, `2`)와 데이터 수신 과정을 `switch-case`로 한 바이트씩 쪼개서 처리하는 구조의 장점(논블로킹)을 이해해 보세요.

### ⚠️ [개선 필요 포인트]: 더블 버퍼링의 패킷 드롭 위험
- **분석 과제:** 현재 `packet_ready` 플래그 하나로만 구현된 버퍼링 구조에서, CPU가 다른 일을 하느라 늦어지는 동안 다음 패킷이 연달아 수신되면 어떤 식으로 데이터가 누락되는지 추적해 보세요. 이를 링 버퍼(Ring Buffer)로 어떻게 바꿀지 구상해 보세요.
